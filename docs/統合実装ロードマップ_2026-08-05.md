## 1. 全体方針

- Markdown を唯一の正とする。Partial Edit Pane・move・indent/outdent はすべて既存の安全な書き戻し経路のみを通す。
- 不確実な境界・構造は編集しない。曖昧なケースは no-op と明示的な理由提示で安全側に倒す。
- 各フェーズは「実装 → 自動検証（tsc / test / build / git diff --check）→ Method Vault 実機受入 → 完了報告」を経てから次フェーズへ進む。
- 実装前に設計方針の承認を得るプロセスを維持する。承認前に既存の書き戻し・Tree 表示・move/indent/outdent のロジックは変更しない。
- **言語方針（2026-08-11 確定、同日中に例外なしで全面適用）**: 本プラグインはユニバーサル（特定言語圏専用ではない）前提であり、Notice・トースト・コマンド名・placeholder など、コード側で組み立てるユーザー向け文言は英語を基本とする。個別チケットが特定の UI 要素について明示的に別言語を指定した場合はその指示に従うが、指定がなければ既定は英語である。方針確定時点で Outline Tree View の空状態メッセージ（`renderEmptyState` 呼び出し2箇所）と Partial Edit Pane の空状態 placeholder に日本語文言が残存していたが、同日中にすべて英語化し、既存UI文言の例外は解消済みである。ソースコード内のコメント（設計仕様書の日本語タイトルの参照や実装指示からの引用等）はユーザーには表示されない開発者向け情報であるため、本方針の対象外とする。

## 3.3 Outline Tree モバイル操作体系（タップ／長押し／メニュー）の確定事項

- 採用した操作体系: 単タップ（未選択ノード）＝選択・フォーカスのみ。長押し（既定 450ms、`src/tree/longPressGesture.ts` の `LONG_PRESS_DURATION_MS`）＝コンテクストメニュー表示。単タップ（選択済みノードへの再タップ）およびメニュー内「Rename」＝インライン編集開始。いずれも `beginRenameForNode(nodeId)` という同一関数を通す（経路を分けない）。
- 「選択済み」の判定は、renderNode が行の選択ハイライト表示に使っている条件 `this.hasFocus && node.id === this.selectedId` をそのまま再利用した。これにより「他ノード選択」と「Tree 外タップ（treeRootEl の blur）」の両方が自動的に「選択解除」として扱われ、専用の解除状態を新設せずに実装要件（解除直後の誤判定防止）を満たしている。
- 長押しで開くメニューは、デスクトップの右クリックメニューと全く同じ `showStructureCommandMenu`/`showListCommandMenu` を呼び出す。両メニューには既に「Rename」項目（`beginRenameForNode` 呼び出し）が存在していたため、本タスク用の新規メニュー項目追加は不要だった。
- 長押し判定は `selfEl` への `pointerdown`/`pointermove`/`pointerup`/`pointercancel`/`pointerleave` リスナー（`renderNode()` 内、`Platform.isMobile` でガード）で実装し、pointermove で一定距離（既定 10px、`LONG_PRESS_MOVE_CANCEL_PX`）を超えた移動を検知した場合はタイマーをキャンセルする。移動距離のユークリッド距離判定は純粋関数 `exceedsLongPressMoveThreshold`（`src/tree/longPressGesture.ts`）に切り出し、`tests/longPressGesture.test.ts` で単体テストしている。

## 3.4 inline rename の安全復帰措置（Phase 5C-1A/1B 補完）の確定事項

- 目的は、rename 開始時の全選択（既存仕様、変更なし）を維持したまま、「全選択＋1キー押下で長いラベルを誤って消してしまう」事故に対する回復コストをほぼゼロにすることであり、rename の起動方法・書き戻し経路・確定後 UX を変更することではない。
- Escape によるキャンセル（`OutlineTreeView.ts` の rename `<textarea>` の `keydown` ハンドラ内、既存の `cancelRename()` 呼び出し）に、`evt.isComposing` による早期 return ガードを1箇所追加した。IME 変換確定前の Escape（変換候補のキャンセル）はこれまで通り IME に委譲され、rename キャンセルとして解釈されない。変換確定後の Escape のみが rename キャンセルとして働く。
- `cancelRename()` は元々 `applyLineEditOutcome`／`editor.replaceRange` などドキュメント本文を書き換える API を一切呼び出さない設計であり（`<input>`/`<textarea>` の DOM 要素を破棄し、Tree の再描画で元のラベル表示に戻すのみ）、Escape キャンセル時に本文へ何も書き込まれないという要件は、ガード追加以前から既存実装によって満たされていた。今回の変更は IME 誤爆防止のガードを1箇所追加したのみで、キャンセル経路自体（＝書き込みなし・Undo 履歴にも残らない）には手を加えていない。
- rename の確定（Enter またはフォーカスアウト）は既存の `commitRename()` → `renameSection`/`renameListItem`（`src/edit/renameBlock.ts`）→ `applyLineEditOutcome` → `editor.replaceRange()` という単一の安全な書き戻し経路をそのまま使用しており、新しい直接書き込み経路は追加していない。
- Undo/Redo の単位分離について、事前に Obsidian/CM6 の Editor API の挙動を実機（使い捨ての一時ノート、DevTools コンソール経由で `editor.replaceRange()`/`editor.undo()`/`editor.redo()` を直接呼び出す方式）で調査した結果、**個々の `editor.replaceRange()` 呼び出しは、`origin` 引数の有無・一致不一致や呼び出し間隔に関わらず、この Obsidian バージョンでは常にそれぞれ独立した Undo ステップとして扱われる**ことを確認した。`applyLineEditOutcome` は rename commit ごとに `editor.replaceRange()` を1回だけ呼ぶ設計であるため、この経験的事実により「rename commit を Cmd+Z 一回で確定前ラベルへ戻せる」「直後の Cmd+Shift+Z で確定後ラベルへ戻せる」「前後の move/indent などの編集操作と Undo ステップが混ざらない」という要件は、CM6 の `isolateHistory` アノテーション等の追加実装なしに、既存の単一書き込み経路のままで満たされていることが判明した。そのため、この項目についてはコード変更を行っていない（`commitRename()` の doc comment に調査結果を記録済み）。
- Method Vault 実機受入（`Test/Unified Outliner Test.md`）にて、section ラベル（`Markdown C`）・list ラベル（list item `333`）の両方について以下を確認した: (1) rename 確定直後の Cmd+Z 一回で確定前ラベルに戻ること、(2) 直後の Cmd+Shift+Z で確定後ラベルに戻ること、(3) Escape キャンセルで本文が変更されないこと、(4) IME 変換中を模した合成イベント（`isComposing: true` の `Escape` keydown）では rename が閉じず、変換確定後（`isComposing: false`）の `Escape` でのみ rename がキャンセルされること。Undo/Redo の確認は、キーボード経由の Cmd+Z がテスト自動化上フォーカスの都合で不安定だったため、DevTools コンソールから `editor.undo()`/`editor.redo()` を直接呼び出す方式で行った（UI 操作としての Cmd+Z 自体は Obsidian 標準機能であり、本測定方法はその内部動作の検証手段に過ぎない）。検証後、テストノートは元の内容（`Markdown C`）に復元済み。
- 非対象（今回変更していない範囲）: move/indent/outdent やドラッグ＆ドロップなど rename 以外の編集操作の Undo/Redo 挙動、rename 開始時の全選択・カーソル配置の既定挙動、複数ノード・複数ファイルにまたがる Undo。

## 3.5 Move block の対象を最小安全ブロックへ／Move section 新設の確定事項

- **背景**: 従来の `Move block up/down` は、カーソルが見出し行になくても実質的に enclosing section 全体を移動する場面があり、コマンド名から想像される局所操作と実際の移動範囲がずれていた。本チケットはこれを、カーソル位置に応じた「Markdown を壊さない最小単位」の移動として再定義し、section 全体を動かす操作は `Move section up/down` として独立させた。
- **最小安全ブロックの解決規則**（`src/move/resolveMoveTarget.ts` の `resolveMoveUnit`）: (1) カーソルが見出し行なら section、(2) list item のマーカー行または本文（継続行）なら list subtree、(3) callout/blockquote/fenced-code/table の内部（confidently bounded なもののみ）ならその複合ブロック全体、(4) それ以外の通常本文なら paragraph、(5) 境界が確定できない場合（scanner が `"ambiguous"`/`"unsupported"` と判定した複合ブロック、あるいはそもそも owner が存在しない行）は拒否し、原文を変更しない。list item の継続行の中にさらに複合ブロック（例: list 項目内の blockquote）が含まれる場合でも、規則(2)を優先し list subtree として解決する——list 継続テキストは既存仕様上すでに list item 自身の一部として扱われているためであり、`findComplexSiblingTarget` 自体は list item を親に持つ複合ブロックも正しく扱える設計だが、カーソル解決の入口では意図的に踏み込まない。
- **fenced-code の特別対応**: `resolver/resolveCurrentBlock.ts` は既存の move/indent 系コマンドのために「fenced code block 内部の行は一律 no-op」というガードを持っていたが、Move block が fenced-code 全体を移動対象にできるようにするため、`resolveMoveUnit` はコードブロック内の行を `resolveCurrentBlock` に渡す前に scanner（`parser/complexBlocks.ts`）へ回すバイパスを追加した。既存ガード自体（move/indent/node-only 系コマンドの挙動）は変更していない。
- **兄弟判定は2系統**: section/list（既存の `BlockNode`）は、従来どおり `move/findMoveTarget.ts` の `prevSiblingId`/`nextSiblingId` を使った兄弟解決をそのまま再利用する（一切変更なし）。paragraph・callout・blockquote・fenced-code・table は `BlockNode` ではなく scanner 専用の `ComplexBlockInfo` であり兄弟関係の追跡フィールドを持たないため、新設した `findComplexSiblingTarget` が「同じ parentId（同じ section、あるいは同じ list item）を持ち、間に空行以外の内容が挟まらない、直前・直後のブロック」を探す。list item や見出しなど他種のブロックが間に挟まる場合は、たとえ同じ parentId を持つブロックがその先に存在しても交換相手とはみなさず拒否する（`no-sibling` または `boundary-unknown`）——安全側に倒す原則を list/section と同様に踏襲している。
- **適用経路**: section/list ユニットは既存の `move/moveBlock.ts`（`swapBlocks`/`insertBlockAt`、cross-section list hop、ordered marker 正規化を含む）をそのまま呼び出す。paragraph・複合ブロックユニットは新設の `move/resolveMoveTarget.ts#moveComplexBlock` が、同じ `swapBlocks` プリミティブ（1行ずつのスワップではなく範囲ごとカット&再挿入）を使って適用する。両者とも既存の `commands/applyLineEditOutcome.ts` を経由するため、Undo/Redo・カーソル復元・no-op 通知の仕組みは完全に共通である。
- **Move section**: `resolveEnclosingSectionId`（`resolveMoveTarget.ts`）が、カーソルの祖先チェーンを辿って最も近い enclosing section の id を返す（見出し行・本文段落・任意深さの nested list item のいずれからも解決可能）。解決した section は既存の `move/moveBlock.ts` にそのまま渡す——これは本チケット以前の `Move block` の挙動そのものであり、ロジックの再利用であって新規実装ではない。
- **Tree の視覚補助**（`src/view/OutlineTreeView.ts`、`styles.css`）: 各行の `.tree-item-self` に `data-kind="section"`/`"list"` 属性を付与し、Tree root に settings 由来の `data-section-highlight`/`data-list-highlight` 属性（`subtle`/`stripe`/`hover`/`off`）を反映することで、色そのものはロジック側に一切埋め込まず CSS（Style Settings 経由でも上書き可能なテーマ変数）のみで表現している。既定値は section が `subtle`（常時ごく淡い背景）、list が `hover`（常時は無地、hover/選択時のみ淡い背景）——「list の視覚補助は section よりさらに弱く」という要求どおり。
- **move 対象プレビューと結果トースト**: `settings.treeKindHighlight.showMoveTargetPreview`（既定 true）が有効な場合、Move block/Move section 実行の直後に対象ノード（section/list はその新しい行番号、paragraph/複合ブロックは enclosing section の行）へ約900msの一回限りのフラッシュハイライトを表示する（`OutlineTreeView.ts` の `queueMoveFlash`/`applyPendingMoveFlash`、CSS の `@keyframes unified-outliner-move-flash-anim`）。`settings.treeKindHighlight.showMoveResultToast`（既定 true）が有効な場合、対象種別を示す英語トースト（例: `Unified Outliner: moved paragraph up.` / `Unified Outliner: moved list item (with 3 nested items) up.` / `Unified Outliner: moved section "Case Overview" up.`）を表示する——初版では実装指示の例示文言に従い日本語で実装したが、「本プラグインはユニバーサルであり、ユーザー向け文言は英語を基本とする」という方針確定（本ドキュメント §1）を受けて英語に修正した。これにより、他の全 Notice（`NOOP_MESSAGES`）との文言体系が完全に統一されている。
- **実装上の注意点（実機受入で発見）**: 当初、トースト/フラッシュのキューイングを `applyLineEditOutcome`（実際のエディタ書き込み）の**後**に呼んでいたところ、`editor.replaceRange()` が同期的に発火させる Obsidian の `"editor-change"` イベントによって Outline Tree の leading-edge デバウンス `refresh()` がその場で走り、フラッシュ用のキューが消費される前に Tree が再描画されてしまい、フラッシュが一切表示されないという不具合を実機テストで発見した。修正は、`outcome.changed`（`applyLineEditOutcome` を呼ぶ前にすでに判明している）を条件に、キューイングを `applyLineEditOutcome` 呼び出しの**前**に移動しただけで、それ以外のロジックは変更していない。
- **設定項目**: `settingsDefaults.ts` に `treeKindHighlight`（`sectionMode`/`listMode`/`showMoveTargetPreview`/`showMoveResultToast`）を新設。既定値はチケット指定のとおり `{ sectionMode: "subtle", listMode: "hover", showMoveTargetPreview: true, showMoveResultToast: true }`。`mergeSettings` はこのネストしたオブジェクトを1階層深く個別マージする（既存のトップレベルキーと同じ「欠けているキーは既定値にフォールバックする」方針）。
- **Move list subtree の独立公開コマンド化について**: チケットでは「必要なら内部APIまたは公開コマンドとして分離してよい」という任意要件だったが、既存の `Move block up/down` が list item にカーソルがある場合すでに list subtree 移動として機能する（`resolveMoveUnit` の規則(2)）ため、新たな公開コマンドは追加していない——`resolveMoveUnit` + 既存 `move/moveBlock.ts` の組み合わせ自体が、要件が求める「内部API」を満たしていると判断した。
- **実機受入結果**（使い捨てテストノート、DevTools コンソール経由で `app.commands.executeCommandById` を直接呼び出す方式で検証): 見出し行上の `Move block` → section 全体移動、section 本文段落上の `Move block` → その paragraph のみ移動（旧来の不具合の再現なしを確認）、list item 上の `Move block` → その subtree のみ移動（子項目数のトースト文言も確認）、callout/blockquote/fenced-code（本文行・開始フェンス行の両方）/table の内部の `Move block` → その複合ブロック全体が移動、`Move section` は本文段落・深くネストした list item のいずれから実行しても enclosing section 全体が移動、交換相手が存在しない場合と間に list item が挟まり境界が確定できない場合の両方で編集拒否（原文不変・適切な英語 Notice）を確認。Tree の section 常時背景・list hover ハイライト・move 対象フラッシュも実機画面で視覚確認済み。テストノートは検証後に削除済み。

## 3.6 Phase 5D-0（基本 block model 拡張 + CompositeBlock 規則基盤）の確定事項

- **命名の経緯**: 本チケットの発注時点の指示書（チャット指示、`docs/phase5d0_basic-block-extension-and-composite-block-spec.md` に全文を保存済み）は「Phase 5C の継続」という前提で書かれていたが、着手前の調査で Phase 5C（scanner/診断基盤）は本ロードマップ §2 のとおり既に完了済みであることが判明した。ロードマップの既存ナンバリングでは「callout/blockquote の Tree 表示・編集統合」全体を指す語として Phase 5D が既に予約されているため、本チケットの作業はその最初のサブフェーズとして **Phase 5D-0** と命名し直した。実装内容そのものは指示書の Stage 0〜2 を踏襲している。
- **範囲**: (1) 既存の `ComplexBlockKind`（`callout`/`blockquote`/`fenced-code`/`table`/`paragraph`）への `thematic-break` 追加、(2) 複数の基本/複合ブロックをユーザー定義規則で1つの操作・表示単位へ束ねる新概念 `CompositeBlock` の認識ロジックと設定 UI。**Outline Tree への実際の表示統合（ノード化・アイコン・displayLabel・move/drag & drop・hoist・Partial Edit 接続）は Phase 5D-0 に含めず、引き続き Phase 5D 以降（§4）の未確定事項として承認待ちのまま残す**——指示書冒頭が言う「3層」のうち、層3（Tree への投影表示層）の詳細指示は本チケットの指示書テキストが Stage 2 の複合化条件列挙の途中で切れており、指示書側から受け取れていない。したがって Phase 5D-0 では層1・層2（解析モデルと複合 block 規則そのもの）のみを実装し、層3は着手しない。
- **用語衝突の回避**: 指示書が言う「複合 block」は、Phase 5C が確立した `ComplexBlockKind`/`ComplexBlockInfo`（callout 等、単一の非原子的 Markdown 構文1つを指す既存概念）とは意味が異なる——指示書の「複合 block」は「複数の基本/既存複合ブロックを空行を挟まず束ねた1操作単位」という、Phase 5C のどの文書にも存在しない新しい概念である。このため実装では既存の `Complex-` 系命名と衝突しないよう、新しい概念には一貫して `CompositeBlock`（日本語では「複合ブロック」ではなく「束ねブロック」または「CompositeBlock」とカタカナ表記のまま用いる）という別名を用いる。`docs/phase5c_block-model-and-tree-display-spec.md` §6 が予約していた「将来の統合 block モデル（`AnyBlock` 等）」とも異なる第三の概念であることを明記する。
- **thematic-break の境界方針**: CommonMark のサンプル方針に倣い、`***`/`___`/`---`（3文字以上の同一文字の連続、行頭0〜3スペースまで許容）を候補とする。ただし `-` のみの並びは Setext heading の underline（`Text\n---`）と字面上区別できないため、直前行（空行を挟まない）が非空行かつ見出し/list/thematic-break 候補自身でない場合は、Setext heading の可能性を優先して thematic-break として **報告しない**（`parser/parseDocument.ts` 自体は変更しないため、この行は既存どおり通常の段落継続行として扱われ続ける——誤って区切り線と判定するより安全側に倒す）。`=` の並び（Setext H1 の underline）はそもそも CommonMark の thematic-break 文字ではないため、この曖昧性は発生しない。
- **CompositeBlock の既定規則**: 指示書が例示した「一行 list + callout」「一行 list + blockquote」（OCR 校正ワークフロー相当）の2つを既定規則として実装する。「一行 list」は継続行・子 list を持たない list item（`ListBlockNode.range` が marker 行1行のみ）と定義する。必須条件（member ranges の非重複・1ブロック1所属・同一 section 内・空行なしの隣接・規則競合時は優先順位最上位のみ採用）は指示書の記載どおり実装し、将来の規則追加に備えて配列で拡張可能な形にする。
- **設定 UI**: 既存の `UnifiedOutlinerSettingTab.display()` に「Composite blocks」見出しを追加し、既定2規則それぞれの有効/無効トグルを設置する（既存の `treeKindHighlight` セクションと同じ、フラットな toggle 群のパターンを踏襲）。

- **既定規則の ID・表示名の確定**: `listCallout`/`listBlockquote` → `imageOcr`/`imageQuote`（設定キー）、`list-blockquote` → `image-quote`（規則 ID）。表示名は `compositeBlock.imageOcr.displayName`/`compositeBlock.imageQuote.displayName` を新設の i18n キーとして解決し（既定規則の生の文字列をハードコードしない）、将来のユーザー定義ラベル（`customLabel`）は i18n 解決より常に優先される設計とした（`model/compositeBlock.ts#compositeBlockDisplayLabel`）。
- **prefix はモデルレベルの意味を持つフィールド**: `CompositeBlockRule.prefix` は装飾用 CSS ではなく、`OutlineTreeCompositeNode.prefix` として Tree ノードのデータに保持し、`renderNode()` が専用の `<span class="unified-outliner-composite-prefix">` として描画する（textContent に含まれるため、copy/paste・既定のアクセシブルネーム計算・DOM テスト双方で prefix を拾える）。空 prefix の場合はこの `<span>` 自体を生成しない（空要素・余分な空白を残さない）。
- **fold identity**: `tree/foldIdentity.ts` に `composite`/`complex-member` 用の occurrence pool を追加したが、member である list item 自身は **composite の path 配下にネストさせず**、従来どおり単独の list item として identity を計算する。これにより、本文編集で複合化条件が崩れて CompositeBlock が消えても、member だった list item の fold 状態は元の identity のまま保持される。
- **カーソル同期は変更しない**: `resolveHighlightedNodeId` は無改修。折りたたまれた CompositeBlock を特別扱いしてハイライトする処理も追加しない（既存の section/list と同じ「折りたたみで非表示になったらハイライトも消える」挙動のまま）。

  CompositeBlock の先頭 member が list 種別かつ `doc.nodes` 上で実際に ListBlockNode として解決でき、
  かつ全 member が自身のソース（list は `doc.nodes`、それ以外は `complexBlocksById`）で解決できる
  場合のみ投影対象とする。実運用の `refresh()` 経路では `infos`/`complexBlocksById` が常に同一パスの
  `doc`/`complexScan` から導出されるため実際には失敗し得ないが、入力不整合に対する防御的不変条件として
  実装し、テストでも検証した。
- **A-2 読み取り専用の明示**: 読み取り専用行に `aria-readonly="true"` / `data-readonly="true"` を
  明示的に付与(`view/OutlineTreeView.ts#renderNode`)。判定ロジック自体も
  `tree/buildOutlineTree.ts#collectReadOnlyOutlineNodeIds`(公開・純粋関数)へ切り出し、
  CompositeBlock 自身・全 member・member 配下のさらなる子孫まで再帰的に読み取り専用集合へ含める。
  以前は `renderNode` の再帰呼び出しへ `insideComposite` という boolean 引数を都度渡す設計だったが、
  refresh() 単位で一度だけ計算する Set に置き換え、Obsidian 非依存で単体テスト可能にした。
- **B fold identity の三分岐化**: 本ファイル §3.7・設計メモ §1.2 が最大リスクとして指摘していた
  `if (kind === "section") ... else ...` という二値分岐は、Phase 5D-0.3 の当初実装から
  `switch` による4分岐(section/list/composite/complex-member、`tree/foldIdentity.ts`)で
  解消済みであることを再確認した。同一 section 内で同名の list item と CompositeBlock が共存しても
  identity が衝突しないこと(kind ごとに独立した occurrence pool を持つため)をテストで明示的に検証した。
- **C child のフォールバック文言**: callout/blockquote の実体ラベルが推定できない場合のフォールバックを、
  汎用の「(空)」から種別ごとの「Callout」/「コールアウト」・「Quote」/「引用」に変更
  (`tree/buildOutlineTree.ts#complexMemberDisplayLabel`)。i18n キーを新設し en/ja 双方を用意した。
- **D 再解析と解消**: 既存の「refresh() のたびに Tree 全体を再構築する」設計により、stale な
  composite/member ノードが残ることは構造的に発生しない(本文編集・ノート切替・設定変更のいずれも
  次の refresh() で完全に再計算される)ことを確認し、本文編集で一致条件が崩れた場合に member が
  重複なく通常表示へ戻ることをテストで検証した。
- **E 非目標の徹底**: `beginRenameForNode`/`showStructureCommandMenu`/`showListCommandMenu` の
  各入口に `readOnlyNodeIds` による二重ガードを追加。行単位の DOM リスナー(dblclick/contextmenu/
  長押し/drag)を経由しない入口 — 具体的には F2 キーボードショートカットと、
  「挿入直後の自動 rename」(`autoRenameAfterInsert`)— についても、選択中のノードが read-only
  なら安全に何もしないことを保証した。特に後者は、新規挿入した list item が同じ refresh 内で
  偶然 CompositeBlock の条件を満たしてしまうケース(例: callout 直前への一行 list item 挿入)で
  実際に到達し得る経路であり、今回の二重ガード追加によって初めて安全に閉じられた。

- fenced-code の fence 終端判定を、`parseDocument.ts` 側の簡略仕様（開始文字種のみ照合）に合わせ続けるか、より厳密な判定へ拡張するか。
- `describeComplexBlockRejection` を実際の UI（Tree のコンテキストメニュー等）へ接続するかどうか。

これらはいずれも、着手前に設計メモを提示し承認を得てから実装する。
